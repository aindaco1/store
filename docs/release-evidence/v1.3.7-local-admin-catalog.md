# Store v1.3.7 release evidence

Date: 2026-09-03

- Candidate branch: `release/v1.3.7-local-admin-catalog`.
- Scope: local dashboard catalog synchronization, service-product support,
  and the operator-approved A Night in Paradiso public event ticket and media.
- Previous independently reversible release: `v1.3.6` at
  `7359bbd4d1543d400cd16a335292027c3fa08683`.
- Shared Platform and Jekyll Template pins are unchanged.

## Behavior and security contract

- Repository products remain canonical. The local sidecar invokes the existing
  fixed Ruby generator, serializes regeneration, watches source changes, and
  atomically replaces only a valid generated snapshot.
- Local saves wait for the running Worker's matching source hash before editor
  refresh. Regeneration/reload/readback failures retain the visible edits and
  do not claim that the catalog is current.
- Local publishing remains test-mode-only with its existing explicit enable
  flag, loopback sidecar, bearer authorization, admin authorization, and CSRF
  boundaries. Production still publishes through the existing GitHub workflow.
- Service fulfillment creates no shipping, download, or ticket artifact unless
  an explicit fulfillment override applies. Canonical checkout remains the
  authority for price, availability, inventory, and fulfillment.
- Paradiso is a $20 ticket with operator-entered inventory 100, QR/calendar
  delivery, and October 24, 2026 event details. The operator explicitly requested
  activation for public purchase during release preparation. This release sets
  it `active`; verification does not create an order or send event email.
- The SEO evidence probe now selects a public product from `/api/products.json`
  instead of assuming the first product directory is public. The full SEO audit
  continues to check private product crawl boundaries.

## Ethical review

- Money and inventory remain server-validated. Product activation follows the
  operator's explicit approval; price, inventory, date, content, and media are
  preserved rather than inferred from the original sponsorship packet.
- No new customer data store, credentials, tracking, admin privilege, or
  marketing enrollment was added. Authenticated failures remain private.
- Local automation is bounded to canonical source regeneration; it cannot
  accept a browser-supplied command or substitute a second catalog authority.
- English/Spanish status messages expose saved-but-not-refreshed outcomes.
  Keyboard/mobile/text-scaling regressions protect the existing admin surface.
- No live charge, customer message, or real catalog mutation is used solely to
  prove release readiness. Provider checks and synthetic tests are reported
  separately from real-world fulfillment and media-rights acceptance.

## Release and recovery sequence

1. Require exact-head **Merge Smoke** and synthetic **Recovery Readiness**.
2. Merge the candidate, tag the reviewed merged commit `v1.3.7`, then dispatch
   **Deploy Production** from `main` with that immutable tag.
3. Verify Worker/Pages deployment, private admin response policy, public crawl
   checks, deployed version, Paradiso public availability, and **Production Posture**.
4. Record unavailable optional provider probes as manual/not-run, not passes.
5. If acceptance fails, redeploy `v1.3.6`; never roll back canonical orders,
   inventory, entitlements, fulfillment, or email state.
6. Only after acceptance, remove merged candidate branches and recoverably
   clean reproducible artifacts. Preserve source/media, dependencies, local
   configuration/secrets, local Worker state, tests, and unmerged branches.
