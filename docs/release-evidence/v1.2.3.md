# Store v1.2.3 release evidence

Date: 2026-08-25

- Candidate branch: `release/v1.2.3-product-publish-progress`.
- Scope: fail-closed archived-product availability plus consistent deployment
  progress for single and bulk product status changes, ordinary product edits,
  and product reordering.
- Previous independently reversible release: `v1.2.2`.
- Shared dependency: Dust Wave Platform `v0.34.1` at
  `ae380c43a16af352ae946f47dd1b7aa4e5b093f0`.

## Behavior and UX contract

- Archived, draft, sold-out, and otherwise unavailable products stay disabled
  when browser inventory synchronization runs. Public catalog filtering and
  canonical Worker checkout rejection remain the authoritative boundaries.
- **Publish changes**, **Activate product**, **Save as draft**, **Archive
  product**, **Mark sold out**, bulk status controls, drag-and-drop, keyboard
  reordering, **Save order**, editor placement, and responsive layout retain
  their existing interaction design.
- One operation-aware dashboard controller tracks the GitHub workflow for the
  exact saved commit and renders **Saved → Deploying → Deployed**, elapsed
  time, failure state, and the bounded GitHub run link. Copy remains specific to
  the selected operation instead of flattening distinct actions into one label.
- Product order saves now return the same deployment metadata as single and
  bulk publishes. Arranged rows remain visible until the matching deployment
  succeeds; failure preserves the saved-versus-live distinction instead of
  immediately reloading the prior order.
- Status semantics are unchanged: Active is public and inventory-aware; Draft
  and Archived are private and unavailable; Sold out stays public but cannot be
  purchased.

## Ethical review

No new customer data, payment behavior, messaging, privilege, or external
provider is introduced. The change reduces operator confusion by distinguishing
saved repository state from deployed storefront state. Existing authorization,
private/no-store response policy, status semantics, and rollback boundaries are
unchanged; no additional ethical-risk mitigation is required.

## Protected merge and deployment gates

Before tagging, the exact reviewed commit must pass the complete pre-merge and
release-smoke gates, including Podman/browser evidence or a documented protected
CI substitute. Create the immutable `v1.2.3` tag only after merge. Production
deployment remains a separate manual action and must use that reviewed tag or
commit through **Deploy Production**; no real product status mutation is needed
as release evidence.
