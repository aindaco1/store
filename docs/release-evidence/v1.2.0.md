## Scope and boundaries

- Registration is opt-in for repository-backed `rsvp` products with an
  explicit `event_details.registration` block. Physical, digital, ticket,
  service, and unconfigured RSVP products retain their existing paths.
- A shared Worker normalizer owns product publication, checkout validation,
  canonical response snapshots, roster projections, check-in, and CSV export.
  The dashboard's guided question builder serializes into the existing JSON
  product field. New question IDs and stored choice values derive from their
  visible labels, remain read-only in the dashboard, and stay fixed after
  publication. Every builder control uses the existing localized help pattern.
  Browser normalization is presentation-only, the Worker re-resolves current
  product data, and no parallel product schema was added.
- Guest names and custom answers remain in memory before checkout and are not
  written to local or session storage. Answers are omitted from email, Stripe
  metadata, logs, and public catalog data.
- Zero-total checkout omits the tip and payment-method controls, labels its
  action `Complete order`, and does not prewarm Stripe. Paid and mixed carts
  retain the existing tip, payment-method, and Stripe-loading behavior. A
  Worker-returned PaymentIntent remains authoritative and restores the payment
  UI even if the browser previously displayed a zero total.
- The root and Worker README files, RSVP/configuration/payment/dashboard/
  workflow/testing guides, public English and Spanish Terms and order-loading
  copy, merge checklists, and changelog describe this same shipped boundary.
  Roadmap-only self-service, invitation, waitlist, messaging, door, series, and
  analytics work is explicitly labeled unshipped and is not claimed by public
  product copy.
- Product editing keeps Publish/Create and Cancel visible in a sticky header.
  Status changes remain pending until the matching action is used, Archived is
  labeled **Archive product**, and the success message distinguishes the
  committed archive from the following deploy/catalog propagation.
- The desktop Price label/help control is contained within a wider field with
  an explicit gap before Status. The same editor uses a single-column narrow
  layout with no horizontal overflow.
- Production posture requires `preview_urls = false`; the checked-in Worker
  retains its custom route and localhost-safe development origins without
  exposing a `workers.dev` or preview URL.
- The root lockfile carries the patched development-only `nanoid` `3.3.18`;
  root and Worker dependency audits report no known vulnerabilities.
