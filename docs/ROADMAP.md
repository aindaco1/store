# Store Roadmap

Store is Dust Wave's static-first commerce layer for products, tickets, RSVPs, and digital downloads. It is live at [shop.dustwave.xyz](https://shop.dustwave.xyz), with checkout, fulfillment, and private administration handled by the Cloudflare Worker at [checkout.dustwave.xyz](https://checkout.dustwave.xyz).

This file is a current capability inventory and forward plan, not release history. The Completed section describes what production Store supports today. Version-by-version changes belong in [CHANGELOG.md](../CHANGELOG.md), and rollout, provider, migration, and rollback records belong in [release evidence](release-evidence/).

## Completed

### Storefront, catalog, and merchandising

- [x] **Repository-backed catalog** — Jekyll renders the storefront from canonical `_products/*.md` records, localized page shells, shared includes, and generated static assets.
- [x] **Public catalog projections** — Product and add-on JSON endpoints support browser discovery, while a generated catalog snapshot gives the Worker the same product, SKU, variant, price, tax, shipping, inventory, status, and fulfillment inputs.
- [x] **Product browsing** — Responsive home and product-detail views provide collection and product-type filters, media, pricing, variants, quantities, availability states, and add-to-cart controls.
- [x] **Catalog visibility controls** — Draft, archived, sold-out, private, and active states consistently control listings, public JSON, SEO metadata, and crawl inclusion.
- [x] **Live public availability** — Inventory-tracked home and product pages refresh confirmed availability once per navigation from a sanitized short-lived projection; static counts remain the failure fallback and checkout remains authoritative.
- [x] **Store-owned cart** — The browser runtime handles variants, quantities, add-ons, coupons, shipping and tax previews, reminder consent, and accessible cart interactions before server validation.
- [x] **Product and media authoring** — Admin workflows support product preview, ordering, publishing, media upload and replacement, explicit alt/decorative state, reference visibility, placement warnings, and source-preserving optimization.
- [x] **Deterministic media inventory** — A rebuildable repository manifest records source hashes, dimensions or duration, derivatives, references, optimization state, budgets, and broken links without creating a second media database.

### Checkout, payments, pricing, shipping, tax, and inventory

- [x] **Server-authoritative checkout** — The Worker rebuilds and validates product, SKU, variant, quantity, price, coupon, shipping, tax, inventory, status, and fulfillment state; tampered carts fail before payment work begins.
- [x] **Paid and free order paths** — Paid orders use Stripe PaymentIntents, while free orders and RSVPs confirm without Stripe.
- [x] **Signed webhook settlement** — Paid orders settle only from verified Stripe webhooks with deterministic idempotency, processing leases, replay protection, and fail-closed amount, currency, identity, and state checks.
- [x] **Payment diagnostics and reconciliation** — Bounded read-only reconciliation, minimized provider evidence, and exported payment details support investigation without creating, retrying, refunding, or canceling charges.
- [x] **Serialized scarce inventory** — Durable Objects coordinate SKU reservations, commits, releases, and availability snapshots so concurrent checkout attempts cannot oversell the same units.
- [x] **Inventory administration** — Admin baselines and overrides are stored separately from derived public/admin projections, and failed or canceled payments release their reservations.
- [x] **Shipping quotes** — Checkout supports USPS-backed quotes, configured origin and presets, delivery choices, and a reviewed fallback policy.
- [x] **Tax calculation** — Worker-owned destination validation and tax quoting support New Mexico GRT defaults, optional provider lookup, persisted order tax details, and one canonical total across checkout, email, admin, analytics, and exports.
- [x] **Coupons and price integrity** — Worker-side coupon validation enforces status, eligibility, windows, and discount bounds; variant and add-on pricing share one normalized contract, and confirmed orders preserve historical unit prices.

### Orders, fulfillment, and customer communication

- [x] **Durable order state** — Store persists order drafts and confirmed orders, then renders token-scoped Order Success pages and fulfillment state in English and Spanish.
- [x] **Private customer lookup** — Generic lookup responses avoid account-existence leaks and deliver short-lived one-time links only when matching orders exist.
- [x] **Physical fulfillment** — Orders retain shipping details, item state, and exportable fulfillment context for operator review.
- [x] **Tickets and RSVPs** — Confirmed items can provide ticket and QR SVGs, calendar files, signed check-in links, attendee search, attendance totals, and CSV exports.
- [x] **Digital downloads** — Confirmed purchases receive durable entitlements with short-lived signed delivery, private/no-store responses, reusable R2-backed files, and item-level revoke or refresh controls.
- [x] **Transactional email** — Store sends localized customer confirmations and super-admin notifications through Resend while keeping Stripe receipt email disabled for first-party orders.
- [x] **Durable email delivery** — Order confirmations, event reminders, and consented abandoned-cart messages use a bounded outbox with idempotency, leases, backoff, delivery evidence, and suppression; provider failure does not roll back order or fulfillment truth.
- [x] **Reminder and referral tools** — Signed resume and unsubscribe links, event reminders, referral and UTM links, QR exports, saved referrals, and suppression controls support consented lifecycle communication.

### Admin, publishing, and operations

- [x] **Protected administration** — English and Spanish admin routes use magic links, signed sessions, CSRF and origin checks, role and scope enforcement, optional Turnstile, rate limits, and private/no-store responses.
- [x] **Store operations dashboard** — Settings, Products, Orders, Downloads, Coupons, Analytics, Marketing, Inventory, users, readiness, plan usage, runtime diagnostics, and observability are available through one responsive dashboard.
- [x] **Repository-backed publishing** — Production product, configuration, and media changes use guarded GitHub writes; local development uses the test-only repository sidecar.
- [x] **Order and fulfillment operations** — Admin can review orders, update item fulfillment, manage download access, check in attendees, inspect imported order context, and export operational data.
- [x] **Session and audit review** — Super-admins can review or revoke sessions, search bounded redacted audit history, and export authorized audit details without exposing raw IP addresses, credentials, or customer rows in list metadata.
- [x] **Readiness and diagnostics** — Sanitized status surfaces cover configuration, providers, secrets by name, bindings, cron work, runtime performance, reconciliation, downloads, reminders, and recovery posture.

### Localization, accessibility, policy, and discovery

- [x] **English and Spanish product journeys** — Localized shells, UI, runtime messages, transactional email, checkout and order states, metadata, and admin workflows share completeness and rendered-evidence checks.
- [x] **Creator-owned product copy** — Product titles, descriptions, and body content remain canonical unless an explicit localized override exists.
- [x] **Accessible responsive interfaces** — Public browsing, product controls, cart, checkout, order lookup, fulfillment, admin navigation, tables, forms, uploads, and async status updates have keyboard, scaling, reduced-motion, live-region, and mobile-overflow coverage.
- [x] **Public policy surfaces** — Terms, shipping, and return information are localized and linked from the storefront and checkout while product and merchant return metadata stay configurable.
- [x] **SEO and crawl integrity** — Canonical and alternate URLs, social metadata, structured data, XML/text sitemaps, robots policy, real modification dates, and post-deploy crawl audits cover public pages while private and tokenized routes remain excluded.

### Performance, security, and runtime reliability

- [x] **Static-first performance** — Public pages are statically rendered, cart code loads lazily, generated assets are minified, fonts and media are budgeted, and responsive assets prioritize only the current LCP candidate.
- [x] **Executable performance budgets** — Build sizes, Lighthouse categories and Web Vitals, resource counts, dashboard timings, Worker routes, and cache policies are enforced by generated-site, Podman, and production evidence.
- [x] **Indexed and bounded reads** — Shared order snapshots, non-PII watermarks, bounded KV reads, queue-state markers, and one-pass R2 readiness prevent routine namespace and object scans.
- [x] **Measured cache controls** — Authenticated admin reads have a shared Workers Cache policy, route kill switches, bounded telemetry, explicit invalidation, deployment-aware evidence, and incident controls; routes remain disabled when measured benefit does not justify them.
- [x] **Private response boundaries** — Admin, order, lookup, download, check-in, reconciliation, and observability responses retain strict CSP, noindex, private/no-store, and no-transform behavior where applicable.
- [x] **Abuse and token protection** — Signed links, request-size bounds, rate limits, network-keyed soft locks, webhook verification, and minimized diagnostics protect authentication, checkout, downloads, fulfillment, and provider callbacks.
- [x] **Data minimization and retention** — Audit, processor, email, suppression, reconciliation, and operational evidence keep explicit bounded retention and exclude raw provider payloads or unnecessary customer data.
- [x] **Production posture monitoring** — Scheduled read-only checks detect actionable drift in secrets, provider routes, origins, bindings, admin posture, localization, and response policy without mutating runtime state.

### Backup, recovery, and operational continuity

- [x] **Canonical recovery inventory** — Every known KV, R2, and Durable Object family has source-of-truth, sensitivity, retention, backup, restore, quarantine, and rebuild classification.
- [x] **Encrypted snapshots** — Guarded tooling captures checksum-covered configuration, deployment, KV, R2, and authorized admin evidence outside the repository without exporting secret values.
- [x] **Safe restore planning** — Restore is plan-only by default, validates manifests and paths, quarantines ephemeral state, rebuilds derived data, and requires explicit conflict policy and production interlocks before writes.
- [x] **Retention and offsite safeguards** — Readiness and retention tooling protects required daily, weekly, monthly, release, and newest snapshots and can verify encrypted copies on a distinct device or approved append-only S3-compatible archive.
- [x] **Recovery rehearsals** — Synthetic Podman drills cover representative order, payment, email, reminder, audit, inventory, R2, quarantine, and derived-repair classes without production data or provider mutations.
- [x] **Inventory recovery** — Aggregate-only reconciliation and a maker/checker Durable Object rebuild workflow require maintenance, webhook, reservation, provider-mode, acknowledgement, and audit controls.
- [x] **No unattended production restore** — Scheduled workflows are limited to readiness and low-traffic preflight; captured-data recovery stays protected, preview-scoped, explicitly enabled, and independently reversible.

### Development, testing, deployment, and shared foundations

- [x] **Host and Podman development** — Fixed local ports, ignored local secrets, production-like containers, isolated Wrangler state, readiness checks, and documented troubleshooting support repeatable local work.
- [x] **Configuration and setup tooling** — Setup, secret-name planning, resource validation, generated catalog synchronization, and local/production dry runs share validated helpers.
- [x] **Comprehensive merge gate** — Secret, content, localization, syntax, unit, security, generated-site, SEO, Worker smoke, performance, accessibility, and responsive browser checks protect every reviewed change.
- [x] **Release and provider evidence** — One release-smoke wrapper and focused evidence commands cover checkout, signed webhooks, fulfillment, accessibility, localization, SEO, providers, recovery, and no-send email paths.
- [x] **Isolated provider-originated payment testing** — A persistent test-mode Stripe webhook targets a no-route/no-cron staging Worker with separate storage, staging-only signing secrets, disabled production providers, and rendered-email dry runs.
- [x] **Manual production deployment** — A reviewed workflow deploys the static site and Worker, purges relevant caches, and verifies production response and crawl behavior; merges and tags do not deploy automatically.
- [x] **Pinned shared platform** — Store consumes characterized framework-neutral primitives from an immutable `dust-wave-platform` gitlink and exact package versions while retaining independent data, business rules, deployment, and rollback authority.
- [x] **Versioned Jekyll golden-project integration** — Seventeen shared Liquid includes and Ruby plugins have one separately versioned, digest-bound template source with explicit check/sync tooling; Store retains checked-in copies and excludes the upgrade submodule from public output.
- [x] **Transactional pre-merge configuration** — The merge gate may derive production-shaped Worker configuration for validation, but always restores the checked-in localhost-safe defaults on success or failure and verifies that behavior automatically.
- [x] **Docs as code** — Architecture, customization, payment, dashboard, security, performance, testing, workflows, backup, ethical risk, and release evidence stay versioned beside implementation.
